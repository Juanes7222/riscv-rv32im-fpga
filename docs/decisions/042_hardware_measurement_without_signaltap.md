# ADR 042: Hardware measurement without SignalTap - counters frozen in the console

**Status:** Accepted
**Date:** 2026-10-19
**Related:** ADR 026 (metric extraction with SignalTap II), ADR 024
(performance counters)

---

## Context

The anteproyecto defines the measurement protocol of the project:

* **Fmax and resource utilisation**: Timing Analyzer and fitter reports from
  Quartus Prime (Activity 3.2).
* **CPI, IPC and throughput**: "internal counters integrated in the processor
  ... verification and logging instrumentation implemented with `cocotb`"
  (§7.1.5, Activity 3.3).
* **Hardware evidence**: "photographic captures and a cycle-by-cycle trace
  table that document its correct operation while running on the DE1-SoC
  FPGA" (Activity 4.2).

SignalTap II appears in none of those points. It was introduced as the
implementation of Activity 3.3 in ADR 026, but it never worked:

1. The SignalTap Tcl API (`stp_open`, `stp_run`, `stp_export`) was removed in
   Quartus Prime 25.1: the `::quartus::stp` package loads but registers no
   command.
2. The hand-written `.stp` files in `stp/` are not accepted by Quartus 25.1
   (`Error (262006): File ... is not a valid Signal Tap File`), so a
   "SignalTap build" silently produces a design **without** any capture logic.
3. `scripts/run_capture.tcl` had a Tcl error (`lindex $argv 1 [default]`) and
   programmed device 1 of the chain (the MAX10) instead of the FPGA.
4. The Logic Analyzer Interface, the API that is available, needs a `.lai`
   file that only the SignalTap II GUI can produce.

## Decision

**Capturing the counters over JTAG is dropped from the scope of the
project.** The hardware measurement is done with the visualisation module
itself, which is already a deliverable of the project (Objective 4):

1. `rtl/shared/perf_counter.sv` freezes two extra counters at the instant
   the program writes to `tohost`: `cycles_at_done` and `instr_at_done`.
2. The console shows them in two new fields, `CyclesToPass` and
   `InstrToPass`, placed by `scripts/add_console_measure_fields.py`.
3. `verification/cocotb/common/test_validation.py` checks that the value
   frozen in the RTL is **identical** to the one the simulation reports, so
   that a photograph of the console is comparable with the CPI table.

The content of the program inside the bitstream is verified automatically by
`scripts/check_mem_init.py`, which compares the `.hdl.mif` files generated by
Quartus with the `.mem` sources.

The cycle-by-cycle trace of Activity 4.2 is generated in simulation by
`verification/cocotb/pipeline/test_pipeline_trace.py`, which records the
state of the five stages on every clock cycle.

## Rationale

* **The anteproyecto does not ask for SignalTap.** The three data sources it
  defines (Timing Analyzer, cocotb, photographs) are covered without it.
* **Cost.** Reimplementing the capture with the LAI API needs a `.lai` that
  only the GUI produces, that is, a manual step that cannot be automated, in
  exchange for a ten-line RTL counter that also improves the teaching
  product: the console shows the result of the measurement the anteproyecto
  discusses.
* **Comparability.** The frozen value is exactly the value cocotb reports
  (checked by an assertion), so the CPI table of the simulation and the
  photograph of the board show the same number.
* **Reproducibility.** `check_mem_init.py` closes the gap SignalTap was
  meant to cover: that the program being measured is the one inside the
  silicon.

## Consequences

* `scripts/create_stp.tcl` writes the `.stp` as plain XML, without the
  removed API, and `scripts/run_capture.tcl` programs the correct device (2)
  and fails with an explicit message when the SignalTap API is missing,
  instead of pretending that the capture worked.
* ADR 026 is superseded in its automatic-capture part; its definition of the
  counters is kept.
* The program loaded in the FPGA must write to `tohost = 0x708`, the
  address the `TOHOST_ADDR` parameter defaults to. The synthetic programs
  were moved to that address; CoreMark uses `0x5000` and needs a build with
  that parameter.
* CoreMark does not fit in the current FPGA instruction memory
  (`IMEM_DEPTH = 2048` words = 8 KB, and its text occupies 10.5 KB), and
  neither does its stack fit in the 2 KB data memory: measuring CoreMark in
  hardware needs a larger memory configuration, and therefore its own Fmax.

## Note on the assembler

The RISC-V assembler (xPack GNU RISC-V Embedded GCC 2.43.1) **expands a
branch with a numeric operand** (`beq x1, x2, 8`) into the inverted form
(`bne` plus a jump), which is not the branch that was requested. With a
symbolic destination the expansion does not happen. The benchmark programs
use symbols; hand-written encodings must be checked with
`riscv-none-elf-objdump`.
